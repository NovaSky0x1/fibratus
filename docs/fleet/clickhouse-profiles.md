# ClickHouse Profiles & Cloud Setup

The fleet server keeps **two persistent ClickHouse connection profiles** — `local` and `cloud` — and lets you flip between them with one click. The active profile drives the live telemetry pipeline; switching drains the in-memory buffer, opens a fresh connection to the new profile, swaps atomically, and closes the old connection. **No service restart**.

This page covers:

- The two-profile model + how it relates to your `fleet-server.yml`
- ClickHouse Cloud setup via the Console API (encrypted credentials, one-click bind)
- Encrypted secret store (`FLEET_SECRET_KEY`, `master.key`)
- Per-account retention propagation across profiles

## Why two profiles

Most operators want one of two ClickHouse deployments:

- **Local / self-hosted** — ClickHouse running on the same VM, native protocol on `:9000`, typically no TLS. Cheap, fast, you own everything.
- **ClickHouse Cloud** — managed service from clickhouse.com, native protocol on `:9440`, TLS required. Scales beyond a single VM, pay-per-bytes-stored.

Without profiles, switching between the two means editing YAML, restarting the service, and hoping you didn't typo the host. With profiles you get:

- Both configs sit side-by-side in the database — flip with one click
- Each profile's password is encrypted at rest in Postgres
- The dashboard's **Database → ClickHouse → Connection** tab edits both in place
- The **Cloud Setup** tab provisions / binds / rotates a Cloud service end-to-end

## Where data lives

| Data | Location | Notes |
|------|----------|-------|
| Profile config (host, port, db, user, TLS, pool) | `clickhouse_profiles` table in Postgres | Plaintext — no secrets here |
| Profile password | `system_secrets` table, key `clickhouse.<profile>.password` | AES-256-GCM, sealed by `FLEET_SECRET_KEY` |
| Active profile pointer | `system_secrets`, key `clickhouse.active_profile` | Value is `"local"` or `"cloud"` |
| ClickHouse Cloud API key | `system_secrets`, keys `clickhouse_cloud.api_key_id` / `api_key_secret` | Encrypted; root only |
| `fleet-server.yml` ClickHouse section | YAML on disk | **Bootstrap only** — secrets get migrated into Postgres on first boot |

After the first successful boot, the YAML's `clickhouse:` block is no longer the source of truth. The server reads the active profile from Postgres at startup. The YAML's `password` field is scrubbed on the next dashboard-driven save.

## Encrypted secret store

The server encrypts every persisted secret with a 32-byte master key loaded in this order:

1. `FLEET_SECRET_KEY` environment variable (64 hex chars). Operators that already have a secrets manager / systemd `EnvironmentFile=` should set it here.
2. `<config-dir>/master.key` file (default `/etc/fibratus/master.key`, mode `0600`, owned by the service user). Auto-generated by the install script, or by the server itself on first boot if writable.

If neither is available, the server refuses to start with a clear error.

> **Back up the master key.** Losing it bricks every encrypted secret in `system_secrets` — there's no recovery short of generating a new key and re-entering every secret via the dashboard.

The install script writes both: `${CONFIG_DIR}/master.key` (the active key) and a copy in the install credentials file (`${CONFIG_DIR}/install-credentials.txt`) — store the credentials file securely and delete it from the host once you've stashed it.

## Editing a profile

Management → Database → ClickHouse → **Connection** shows both profiles as cards:

- **Active** profile gets a green badge and no "Use this profile" button (it's already in use)
- The other card has **Use this profile** which hot-swaps when clicked
- Each card has **Test** (round-trip a `SELECT version()` against the profile's stored creds) and **Save** (persist edits; password optional — leave blank to keep stored)
- **Advanced** collapsible exposes pool sizing and dial timeouts

Saving never affects the live connection on its own. Switching the active profile is what triggers the hot-swap.

## ClickHouse Cloud setup (one-click)

Management → Database → ClickHouse → **Cloud Setup** drives the full Cloud flow:

1. **Cloud Console API credentials** — Create an Admin role API key at [clickhouse.cloud → API Keys](https://console.clickhouse.cloud/), paste Key ID + Key Secret. Saving validates by calling `ListOrganizations` against the API. Stored encrypted.
2. **Pick organisation** — Lists every org the API key can reach.
3. **Pick or create service** — Lists every service in the chosen org, OR click "+ Create new service" to provision one (name, provider, region, tier).
4. **Bind**:
   - **Existing service**: hit **Rotate & bind** — we call `ResetServicePassword` on the Cloud API, capture the new password, write it to the cloud profile, and (if cloud is the active profile) hot-swap the live pipeline. The Cloud API never returns existing service passwords, and rotating from the Cloud console doesn't show the new value either, so this is the path that actually completes.
   - **Newly created service**: the API returns the generated password at creation time; we capture and store it automatically.

Once bound, switch from local → cloud (or vice-versa) any time from the Connection tab.

## Per-account retention

`accounts.telemetry_retention_days` stores the per-account TTL in days. When an admin updates it (either via Super Admin → Accounts or Management → Account), the server runs:

```sql
ALTER TABLE telemetry_<sanitized-org-name>_<id8>
MODIFY TTL toDateTime(timestamp) + INTERVAL <N> DAY DELETE
```

…against whatever ClickHouse is currently active — Cloud or local. After a hot-swap, future retention edits naturally target the new active profile.

The `MODIFY TTL` itself is metadata-only and instant; ClickHouse reclaims aged-out rows during background merges (within a few hours of the threshold). Cloud's merge cadence is independent of self-hosted's.

## Verifying TTL on the live tables

From the dashboard's **Query** sub-tab:

```sql
SELECT name, engine_full
FROM system.tables
WHERE database = currentDatabase() AND name LIKE 'telemetry_%'
```

The `TTL` clause shows up at the end of `engine_full`. Long values truncate by default — click the cell to expand.

For storage / oldest-row diagnostics:

```sql
SELECT
    table,
    sum(rows) AS rows,
    formatReadableSize(sum(bytes_on_disk)) AS size,
    min(min_time) AS oldest_event,
    max(max_time) AS newest_event
FROM system.parts
WHERE active AND table LIKE 'telemetry_%'
GROUP BY table
```

## Troubleshooting

| Symptom | Cause | Fix |
|---------|-------|-----|
| `Use this profile` is greyed out | Profile is disabled or has empty host | Edit, set host + tick Enabled, Save, then activate |
| `dial tcp :9440: connect: connection refused` | Host field is empty (placeholder text only) | Same as above |
| `Database X does not exist` after switching to cloud | Profile inherited a custom DB name; Cloud has only `default` | Edit cloud profile → set Database to `default` (or create the DB on the Cloud service) |
| Auth fails after restart | Mid-bind crash left password in secret store but YAML host points elsewhere | Switch profile via dashboard or clear the orphan secret-store row |
| `secrets: FLEET_SECRET_KEY is not set` on boot | Master key file unreadable or env var missing | Ensure `${CONFIG_DIR}/master.key` exists, is owned by the service user, mode `0600` |
